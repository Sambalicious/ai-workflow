## Test strategy

All 98 in-scope IDs map to either an executable check or a named human check: 92 automated rows across unit (pure guard, signature and scheduling decisions), integration (agent service plus real persistence, driven through a simulated WhatsApp boundary) and e2e (owner-facing order list and invoice views in a browser), plus 3 rows of type `manual`. The product stack does not exist in this repository — there is no `PROJECT_ROOT` app for EPIC-0005, only the spec set — so the paths below are the proposed layout under the project test root and must be confirmed by the implementation owners before the authored files land; they are not evidence that any file exists. The WhatsApp Cloud API is third-party and cannot be driven live from a test, so every journey row declares one test double on that boundary only: a signed inbound-message injector plus an outbox capture for outbound messages, with the first-party service, verification logic, scheduling and database unmocked. Payment-provider behaviour is likewise declared as a fake behind a provider seam (Q2 still open, S05 Gaps). Time is controlled by an injected clock plus an explicit `advance`/`fire` trigger, and every clock assertion names the instant it uses. Assertions never read the model's prose for exact copy where no copy deck exists; they use amount extraction, field-level reads and the deny-lists the specs themselves state, and each such substitution is named in the row and in *Spec defects found*. Manual rows stay pending until a named human supplies candidate-bound evidence. Author and verifier are the same session for this derivation only; execution in a later session is a new candidate and invalidates nothing here because nothing here is a result.

## Derivation conventions

Shared seeds (order numbers are per-spec, per each file's fixture note; a cross-spec seed must allocate them separately):

- Vendor `V1`, owner number `+2348030000001`, buyer `+2348030000002`, second buyer `+2348030000003`.
- S03: order `#2042` = 1 × Ankara gown – L at ₦18,500, no delivery fee; gown record quantity 5.
- S05: order `#5042` = 1 × Ankara gown – L at ₦18,500 + Lagos Mainland ₦3,000 = ₦21,500 (see D-01: S05_017 and S05_018 contradict this).
- S07: Ankara gown – L ₦18,500 qty 5, Ankara gown – XL ₦20,000, Silk scarf ₦4,500, Lagos Mainland zone ₦3,000.
- S09: order `#1042` = 2 × Ankara gown – L at ₦18,500 + Lagos Mainland ₦3,000 = ₦40,000.

Shared oracle helpers, all test-owned and independent of the implementation (`tests/support/oracles.ts`):

- `amounts(text)` — extract every currency amount, normalising `₦18,500`, `NGN 18500`, `18500`, `₦15k` to integer naira. Every deny-list assertion uses this, so "no amount" means `amounts(text)` is empty or a subset of a named allow-set, never a text search.
- `listedSet(seed)` — the unit prices, delivery fees and listed totals for the seeded catalogue.
- `outbox(chatId)` / `escalations(vendorId)` / `order(no)` / `invoiceLines(no)` / `overrideRecords(no)` / `record(sku)` — read surfaces per G-01…G-10.
- `clock.set(instant)`, `clock.advance(ms)`, `clock.fire(schedulerTick)` — the time seam per G-13.
- `boundary.deliverSigned(payload)` / `boundary.deliverForged(payload)` — the WhatsApp and provider doubles per G-05 and G-06.
- `race(a, b)` — deterministic interleave per G-13; a row that needs it names the interleave point, and a row whose interleave cannot be forced is flagged in the row.

Copy rule: no copy deck exists (stated in all four files' Gaps). Rows therefore assert either an exact string quoted in the spec, an amount-set predicate, a field-level read, or the specific deny-list the spec states. Each row says which.

## Edge cases and adversarial scenarios

Beyond the case IDs, these belong in the authored files as additional scenarios and must not be used to satisfy an existing ID:

- Input: an empty message body, a message of maximum WhatsApp text length, a message of only emoji, a receipt image with no caption, two media items in one message, and an amount written as "18.5k", "18500.00", "NGN18,500" and "₦18,5OO" with a letter O, all against the `amounts()` normaliser — the normaliser is the weakest link in every deny-list.
- Input: a haggle naming two items at once, a haggle that quotes the correct listed price and asks for a delivery fee waiver, an owner-impersonation message from a second number that is not the registered owner.
- State: a buyer message that arrives after a take-over, an escalation whose order is cancelled between the trigger and the owner's answer, a manual paid mark on an order already paid by webhook, and an unpaid mark on an order whose stock was decremented.
- State: an invoice whose expiry passes while the virtual account is still pending creation, and a reminder due at the exact instant the vendor changes its reminder interval.
- Data: an inventory record with a null price, a negative quantity, a quantity below the reserved units, an item listed in two categories, and a delivery-fee record absent for a zone the buyer names.
- Data: an order whose stored total disagrees with the sum of its lines, which is exactly the failure S03_020 and S07_005 are meant to catch.
- Scale: 51 adversarial prompts rather than 50, a vendor with 500 open escalations and a scheduler tick that must remind all of them inside one window, a chat with 200 messages before the take-over, and a webhook burst of 100 identical deliveries.
- Rate and replay: a provider webhook delivered out of order — an older reference after a newer one for the same order — and a webhook whose timestamp is outside any replay window the contract names.

## Risk areas

- The amount guard (S07 R7_03/R7_04). It is the only thing standing between a hallucinated price and a buyer, and it is also the component most likely to block correct replies. A guard that passes everything and a guard that blocks everything both look green on TC-067 alone.
- Escalation state across four surfaces — the buyer chat, the owner chat, the escalation record and the order. S03_009 and S03_025 are the two places where two writers touch that state at once, and they are the two cases with no seam to force.
- Idempotency. Five separate cases (S03_011, S03_015, S05_015, S05_016, S05_025/S05_027, S09_002) assert "exactly once" against six different dedupe keys, and a single missing key shows up as a double decrement, a double invoice line or a duplicate confirmation rather than as one obvious failure.
- The inventory counter model. S05_017, S05_018, S09_005 and S09_006 cannot all pass under a single-counter implementation, and the PM has not confirmed the two-counter reading. This is the highest-probability source of a blocker that looks like an engineering defect.
- Time. Reminders, invoice expiry, the 24-hour customer-service window and the 60-second confirmation deadline all key off instants that no contract defines. An implementation can be correct and still fail TC-021 to TC-025 and TC-059 to TC-061 on granularity alone.
- Owner attribution. TC-054 to TC-058 and TC-030 depend on a registered-owner check that no criterion states, and TC-055 is the only case that tests a non-owner trying an owner command. One missing check turns S05_024 into a full payment-status bypass.
- Order-scope authorization. TC-094 and TC-095 are the only two cases preventing a buyer from reading another buyer's order, and they currently also enable enumeration (D-11).
- Copy-driven oracles. 26 rows depend on unstated copy. When the copy deck lands, several rows tighten and at least TC-004, TC-005, TC-013 and TC-080 change their assertion mechanism, so they must be re-derived rather than merely re-run.
- The 50-prompt suite (TC-026). Its composition is unspecified, so its green result says as much about the author's prompt choice as about the agent. It should never be the only evidence for AC3_05.

## Coverage gaps

- Model behaviour under paraphrase. Every price and escalation case uses fixed prompts; nothing measures whether a reworded haggle still escalates. Only manual TC-031 and TC-085 reach novel phrasing, and both are human and sparse.
- Multi-turn drift. S03_028 covers six turns in one chat. Nothing covers a buyer who haggles across two chats or two numbers, which is the cheapest way to get a second bite at a discount.
- Provider reality. Every payment path runs against a double. Whether a real provider's webhook arrives with the same header casing, retries on a non-2xx, or sends a partial amount is only observable in a sandbox, and no sandbox is authorised.
- WhatsApp template approval and delivery. TC-053, TC-060 and TC-061 assert that a template is used and names the order; they cannot assert that the template is approved, that it renders, or that it is delivered.
- Latency under load. AC7_07 has one manual check at 200 messages over 30 minutes and no automated percentile at realistic concurrency, so a regression that only appears at 50 concurrent chats is invisible.
- Owner experience of a stale escalation. Nothing tests what the owner sees after days; the spec records the gap and no case picks it up.
- Localisation. S07_017 covers one Yoruba sentence. Hausa, Igbo and mixed-language messages have no case, so the fallback to the owner is untested for two of Nigeria's three main languages.
